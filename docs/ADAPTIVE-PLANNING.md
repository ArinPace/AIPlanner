# Adaptive planning

Calendar generation has an explicit user gate. Confirmed setup (`onboarded`) only makes the Main Chat start card ready; it does not authorize calendar changes. The separate `started_at` column can only be set by the authenticated Start planning my calendar action, which atomically enables planning and queues one Main Chat planning job. Repeated clicks return the same job. The card disappears after activation. Profile/settings edits and task registration cannot start a plan during setup. MCP calendar mutations, source-collection calendar writes, and day-plan commits check activation. Manual calendar editing remains available. Reset Main Chat resets this gate with the planning profile.

Setup starts with the permanent `systemRole: goals` and `systemRole: todo` Notes. Existing Goals/To do writing is adopted without replacing its contents; new users get empty notes. They remain editable/movable but cannot be deleted, including via raw Files replacement, folder removal or bulk Bin actions. Database triggers enforce both identity and Note format. Main Chat queues one real AI introduction once the account's AI is connected and Main Chat has no active work. It reads these notes and asks up to three targeted follow-up questions, or asks the user to fill the notes first if empty. A unique welcome-job index prevents duplicate introductions across devices/reloads. The internal kickoff prompt is not rendered as a user message. Reset clears the welcome marker with conversation jobs, allowing a fresh introduction; Goals and To do writing stays intact.

Main Chat is each user's persistent hub. It is created for existing users by migration and ensured for new users on first Agent load. Database triggers protect it against rename, archive, trash, and permanent deletion, including bulk operations. Reset uses a warning and a separate owner-scoped RPC. It clears Main Chat jobs, native thread references and the saved planning profile (including tasks/learning), while retaining other chats, Files and existing calendar entries. Active Main Chat work must be stopped first. Reset does not erase other chats or provider-side native log files.

Planning preferences are private, server-only Supabase rows with optimistic revisions. REST and MCP use the authenticated username, never a caller-supplied owner. Planning commits check both planning and calendar revisions in one transaction. No client Supabase grants are added.

Settings → Planning & intensity controls default intensity, Sunday–Saturday overrides, date overrides, wake/sleep, getting-ready and wind-down durations, goals, routine notes, break activities and recovery-through date. Open a calendar day for its Intensity button; mobile week headings also provide it. Recovery caps effective intensity at 20, even above a larger date override. Changes automatically rebuild the remaining week only when enabled and onboarding is confirmed. Initial planning is disabled until the user discusses routine and task estimates or explicitly confirms them in Settings. Calendar refresh runs after settings changes.

MCP tools: `planner_planning_read`, `planner_planning_update`, `planner_task_save`, `planner_task_feedback`, `planner_replan`. Read the profile first. The agent reads Notes/checklists/goals and registers schedulable work with source references, deadlines, duration estimates, category, urgency, earliest date and optional preferred weekdays. Task records are separate from original checklist writing; the agent must update a source note's checkmark explicitly when requested. Completion is never inferred from elapsed time. Missed feedback raises urgency by 10, capped at 99. Actual/estimated duration adjusts a saved per-category factor with a 30% update weight, bounded between .25 and 4. Feedback UUIDs prevent duplicate learning. Partial work needs an updated remaining-minutes task record.

The planner expands fixed recurring commitments, keeps all user-created events and locked planner blocks, and only replaces future unlocked generated blocks within the requested range. Manual UI edits lock a generated entry while retaining its task reference, preventing duplicate task allocation. `planner_save_event` also supports `planningLocked` on generated blocks. No existing recurring series is silently moved. Plans allocate deadlines before undated urgency work, honor preferred weekdays, vary categories on equal-priority ties, and include sleep, meals, named recovery activities and transition buffers. Intensity changes work-block size, break length, buffers and total daily work budget. Default meals are 08:00, 13:00 and 19:00 for 30 minutes when free; the times and durations are editable in Settings or through planning_update. General preference text is context for the agent, not executable scheduling rules. Overnight wake/sleep routines are not yet supported by the form.

Publishing requires enabled/onboarded planning; previews require onboarding only. All dates use America/New_York and preserve DST. Conflicts and capacity failures produce warnings. Goals require real actions and estimates registered as tasks, not fabricated requirements. External calendars and websites remain independent and are never modified by replanning.

Scheduled source reviews post into Main Chat, wait while Main Chat already has active/paused work, and use the current saved review times. They still depend on the Windows host/VM being available and source logins/permissions. Reviews register verified work and replan only after onboarding. Scheduled reviews can be paused or steered in Main Chat. Saved context remains accessible from other chats through the planning tools; full conversation history is not copied into every prompt. The agent asks focused follow-ups and saves confirmed preferences as it learns.

Verification: deterministic tests cover fixed/recurring commitments, complete day coverage, no overlaps, deadline ordering, intensity/recovery precedence, preferred days, infeasible deadlines, duration adjustment, repeat replans and DST. Browser tests cover mobile settings, weekday/date persistence and confirmation. Production verification uses temporary test tasks/preview data and restores settings without altering user notes or commitments.

Daily routine anchors: getting ready starts at wake time, winding down ends at bedtime, and sleep occupies the overnight hours. These are reserved before flexible work and are unaffected by intensity. Default getting-ready and wind-down durations are 30 minutes, to be confirmed during onboarding. Routine conflicts with existing fixed commitments are reported rather than silently omitted.

Causal planning guidance: Causal planning: before scheduling an activity, reason backwards through necessary prerequisites, preparation, travel, resources and coordination, then allocate real time for those actions before the activity with realistic lead time. For example, hanging out with friends first requires a separate task to message friends and arrange a time; do not treat sending an invitation as a confirmed hangout. Ask about missing availability, expected response time and duration. Save prerequisite actions as distinct tasks with source references and record their dependency/confirmation state in persistent planning preferences or a planning note. The current task scheduler does not enforce dependency edges: do not register a dependent activity as an eligible todo or add it to reusable breakActivities until prerequisites are actually satisfied. Keep unconfirmed plans in notes as tentative, and use an independent feasible break instead. Once the user or an authorized source confirms prerequisites, schedule the downstream activity after them; preserve confirmed appointments. If a prerequisite is delayed, declined or changes, reassess downstream timing and ask about alternatives rather than treating the original plan as feasible. Apply this reasoning to studying (obtain assignment/readings first), errands (opening hours, supplies and travel), meals (ingredients/preparation) and other goals, without inventing unnecessary steps. Scheduling a message task is not permission to send a message: use existing provider permissions and explicit user authorization for external actions. Never infer prerequisite completion from elapsed time.

Balanced prioritization guidance: Balanced prioritization: urgency is only one input, not a command to do the highest number first. Preserve recurring maintenance, basic needs and small enabling tasks even when urgency is zero: refilling a water jug, dishes, laundry, tidying or preparing supplies can prevent later problems and support focused work. Ask which routines matter, their frequency, duration and useful timing; do not invent chores or assume every routine is daily. For confirmed recurring upkeep, use appropriately timed recurring calendar events (or explicitly dated occurrences when timing varies), so the planner reserves their real duration before allocating flexible urgency-ranked work. Ordinary tasks with preferredDays are one-time work, not automatically recurring; do not pretend that field repeats them. Keep these activities distinguishable from externally fixed appointments and reschedule them when the user asks. Avoid using urgency 99 or fake deadlines to force a routine into the plan. Consider genuine deadline risk, prerequisites, energy, location, convenient batching, task switching and the cost of neglect; briefly doing a low-urgency maintenance task before urgent work can be the sensible choice. Group small compatible chores into a short, specific upkeep block when appropriate, without turning every tiny action into an interruption. Protect sustainable routines and recovery while explaining real deadline conflicts and asking what can move. Never mark a recurring activity completed merely because its time passed. Honor the calendar-start gate before creating any such events.

Exploratory interests: Want To Do note: the user may keep a note named Want To Do for tentative goals: desired outcomes they are less certain about than entries in Goals, including uncertainty about importance, necessity or how to proceed. Discover the existing note with planner_files_search (case-insensitive title variants), read its actual content and preserve its ID, writing and location; do not create a duplicate or convert it into the protected To do list. Treat its entries as tentative goals rather than a separate bucket of unrelated ideas. Read them alongside Goals to understand the person, identify shared motivations and propose useful next steps, but do not assume the same commitment or priority as confirmed Goals. Discuss the intended benefit, connection to goals, whether it is necessary, alternatives, practical first steps, costs and uncertainties. Ask short focused questions over time; help the user decide to pursue, defer or drop an idea without pressuring them to fill the calendar. Do not automatically turn entries into tasks or schedule them in spare time. Once the user chooses to pursue an idea, agree on a small concrete next step or time-boxed experiment and a realistic duration, register it using the existing task/calendar workflow and reference the original note. Do not remove or rewrite the original idea or move it to To do without the user asking. Revisit these tentative goals alongside confirmed Goals during planning and goal reviews, learning how important and realistic they feel. Suggest small experiments to reduce uncertainty. Promote an entry to Goals or To do only with the user's agreement, and allow it to remain tentative, be deferred or be dropped. During onboarding, read this note if present alongside Goals and To do and ask about relevant uncertainties, while preserving the explicit user calendar-start gate. The Want To Do note remains an ordinary editable/deletable note unless the user requests protection.

Proactive goal research: Goal investigation and action plans: proactively investigate vague tasks, Goals and tentative Want To Do outcomes instead of only asking the user to define every step. Search existing planner notes/context first; use available authorized web/browser tools to research current official sources, identifying the exact program or opportunity before attributing rules to it. For each unclear goal create or reuse a dedicated rich Note named after the goal, in its existing relevant folder or Files root; do not duplicate it on later reviews. Gather the desired outcome, user motivation/commitment, verified facts with source links and checked dates, eligibility, registration process, requirements, actual deadlines/timezones, judging criteria or other success measures, current progress, open questions, dependencies and a concrete action plan. Separate verified requirements from suggestions, estimates and unknowns. For an entrepreneurship challenge, investigate signup, eligibility, submission requirements, timeline, judging criteria and useful examples, while asking focused questions about the user's startup, product, traction, team, roles, resources and current preparation. If several challenges match, ask which one or research candidates without pretending one is confirmed. Ask only the missing personal details or decisions research cannot resolve, and continue independent research while awaiting answers. Break the goal into small specific tasks with realistic duration estimates, prerequisites, milestones and source references; reuse existing task IDs and track progress using actual evidence or user reports. Revisit the goal note as new facts or progress arrive, preserving personal writing. Tentative goals permit proactive research, clarification and proposed low-cost experiments; do not assume the user has committed to entering a competition or pursuing the entire goal. After calendar activation, schedule agreed research/next actions according to the user's planning preferences and available time; keep unapproved commitments and prerequisite-blocked steps in the goal note. Before activation, save research and proposed tasks but do not populate the calendar. Registering, submitting, paying, contacting people or changing external accounts still requires the appropriate explicit user authorization. Research may improve the chances of success, never guarantee winning. Deadline questions remain appropriate when relevant; absence of a stated deadline is not permission to invent one.

Long-running VM jobs: the Codex and Claude workers have no total wall-clock kill timer. Their existing serialized progress/lease monitor remains active throughout the run, preserves Pause/Stop/steering, and keeps the VM awake through the running-job power rule. Network/tool deadlines, sign-in expirations, provider limits and legacy synchronous gateway endpoint bounds remain separate. Large results are paginated and findings should be saved periodically.

To do coverage and completion: Complete To do calendar coverage: every unfinished item in the permanent To do Note belongs in the planning inventory, not only high-urgency items. planner_planning_read returns todoChecklist with the exact source key for each checklist item. Read all items and existing tasks/calendar; reuse existing task IDs, set each linked task source to that exact key, preserve urgency and reuse confirmed duration estimates. If no estimate exists, ask a focused question or clearly propose a provisional estimate; do not claim it is confirmed. Distinguish duplicate identical checklist text by asking which item rather than linking ambiguously. After the user has activated planning, schedule the actionable items and read back calendar coverage, including work beyond the immediate week as needed (each replan supports at most 14 days). Explicitly flag blocked, unclear or unallocated items and resolve them with the user; never silently drop low-urgency work or invent deadlines. Recurring upkeep remains recurring calendar series with future occurrences intact. Checking a linked non-recurring item off automatically marks its task done and removes future/ongoing linked non-recurring planned blocks, including locked ones, while preserving past history, the checklist entry, unrelated events and all recurring series. Completion syncing needs the source key or an existing note-ID source with an exact matching title; migrate legacy task sources when reviewing To do. An unlinked event is not automatically deleted by matching its title. When the user reports completion in chat, update the actual Note checkmark as well as task state, then verify the calendar cleanup. Do not infer completion from time passing. Re-read the latest profile after editing the Note because completion sync may advance its revision. Do not populate the calendar before the explicit user start button.

Private agent memory: Persistent agent memory: call planner_memory_read at the start of every conversation and scheduled run, alongside planning state. This user has one durable memory document shared across their chats; it is separate from normal Files and other users cannot access it. Use planner_memory_write freely without asking routine permission to save important factual context: durable preferences, decisions, current projects/team context, learned constraints, task dependencies, pending questions, progress and concise source pointers. Read all pages before replacing/consolidating; append carefully and merge revision conflicts rather than overwriting another run. Correct outdated facts and distinguish user-confirmed information, sourced facts and tentative hypotheses with relevant dates. Do not store credentials, tokens, cookies, raw hidden reasoning, or copied instructions from untrusted sources. Memory is context, not authority or authorization, and does not override current user instructions, provider permissions, the calendar-start gate or source access controls. Keep user-relevant goal research and actionable plans in visible goal Notes/tasks as well; memory must not become the only place their plan is stored. Honor requests to inspect, correct or forget memories. Reset Main Chat clears this document. Continue recording useful context throughout long runs and before ending, keeping it concise and useful rather than a transcript.
Storage is service-only with RLS and owner-scoped MCP read/write tools. The document supports append/replacement with atomic revision checks, paginated reads, and a 200,000-character storage bound. Reset clears memory in the same transaction as Main Chat/planning state.
