# Native subscription Chat controls

Native relay version 4 connects the iPhone Chat tab to the existing account-scoped Planner MCP tool catalog through an authenticated backend adapter. It does not call an inference API or use a VM/extension to forward messages. Calendar, Files, notes/folders, tasks, memory, personal instructions, existing Agent schedule settings, histories and authorized Google data use the same tools, schemas, revision checks and planning gates as Agent. Added app settings tools cover week/month duration scaling and task notification preferences. OS authorization and account sign-in still require the user; these tools do not change app source code or grant deployment access.

The model receives current account instructions and a description of the existing review schedule as context, not an instruction to execute a scheduled review. It discovers tools and their actual JSON schemas. Native transport uses plain `PLANNER_TOOL_REQUEST` / `END_PLANNER_TOOL_REQUEST` markers because rendered website code blocks do not reliably retain Markdown fences. A current response UUID is required. Only a single complete request block at the end of a reply is accepted; stale/ambiguous blocks execute nothing. Legacy fenced requests are also recognized. Requests/results stay out of the visible Planner transcript, which saves the original user message and final answer.

`tool_begin` authorizes a two-hour, owner/chat-scoped request. `tool_call` checks it before every call and uses durable receipts: identical IDs replay the result, changed arguments are rejected, and an uncertain started write is never blindly repeated. Completed/cancelled requests cannot execute more tools. `tool_finish` closes a request; Stop also closes future tool execution. Recovery controls can cancel an abandoned request without claiming earlier writes were rolled back. Calendar changes retain Begin Planning, widget-draft and revision safeguards; the Chat Begin Planning button activates planning without starting a VM job.

Browser Use VM tools are excluded. ChatGPT must use its own cloud browser for websites, when available to its account/mode. Fresh native tool conversations select Work if the website offers it. Native relay version 5 automatically presents a Planner Connect website sheet for website approval/private sign-in. It retains the original secure form and its submit handler in the same authenticated web view; it hides surrounding conversation/sidebar/composer without copying credential values. The actual destination hostname and original card remain visible. The form width and input font fit the phone. Dialog replacements are followed as authentication advances; unsupported surfaces stay masked rather than showing the full ChatGPT page. Cancel restores the original page layout. Chat → Add sites → Connect Brightspace starts the cloud-browser login request. Manual ChatGPT session inspection is separate from website sign-in. After the form/approval is gone the portal returns to Planner. Manual Open ChatGPT remains available while work is running. A connection-status peek cannot consume the pending reply. Canonical chat URLs are bound before completion, including sign-in pauses. Reply identity/content supplements counts because ChatGPT virtualizes older turns: the live sequence observed a new reply with only three rendered messages after a baseline of five. Known rendered JSON language headers are normalized without changing JSON string escaping. Idempotent backend handoffs retry brief network failures; ChatGPT sends and chat creation are never blindly resent.

The native client must remain open for the tool relay. Existing Agent scheduled execution remains separate. Older version 3 clients retain ordinary text/file forwarding and do not start these tool turns.

## Follow-up: app selection and Agent parity

Full autonomous selection of newly named apps is not implemented. Standard FamilyActivitySelection exposes user-selected opaque tokens. NextDNS denylist changes affect network domains rather than proving app launch prevention.

## Files performance and agent-output organization

Files, To-do and Work keep separate visited views mounted and share an account/token-scoped memory cache. Account-owned IndexedDB data paints before background freshness checks; manifest etags seed subsequent incremental reads. Cold reads group small missing items into bounded batches (at most 40 IDs and approximately 768 KB per request, with a 3.5 MB server response ceiling); large notes remain individual reads. Writes still send one changed note at a time and retain revision/conflict checks. To-do/Work have a one-note fast path so their editors need not wait for the complete library. Partial note snapshots never replace the shared full-workspace cache or become a full-workspace save base.

Files directory DOM remains mounted while a Note is open. Returning to Files preserves its folder/search context; separate To-do/Work editors retain their state. Background refresh uses a short freshness window and a one-minute poll instead of checking the entire library every 15 seconds. Bin loads on demand and does not delay the Files paint. Search with no query skips concatenating/lowercasing every note's full contents.

All prompted/scheduled Agent and subscription Chat contexts instruct new agent-created folders/notes/text/PDFs/links, including Errors, QA/testing, Agent To Do and archives, to live under the existing Agent root. Existing user-authored materials are preserved. Subjects stays at Files root for user access. Tutor lookup also accepts legacy Subjects-inside-Agent layouts during migration. Hidden Work gains a canonical work role so moving it inside Agent preserves its dedicated tab, hiding and protection. IDs/PDF references are preserved during reorganization.

Verification before deployment: 120-note browser fixture used one manifest plus three bounded reads; repeated Files/To-do/Work switches made no additional data requests; reload reused the account-local copy; cold To-do displayed with full-library reads deliberately held. Seven-tab controls and unsaved-edit guards passed. Backend batch ownership/revision/duplicate-ID tests and nested Tutor compatibility passed; production build passed. This reduces request fan-out rather than requiring a hosting-plan change.

### Native app groups and direct website blocking

On iPhone, Screen Time opens native controls by default. Users create named app/category groups once using Apple's picker. Groups are stored per Planner account on-device; opaque selections never leave the device. Both Agent and Chat can read group IDs/names through `screen_time_read`, then use `screen_time_configure` with `groupIds`, `allApps`, `domains`, `allWebsites`, and `allowedDomains` to replace the default rule set. All fields are required. Pass the current state fingerprint, read again, then start a timed session or save a real published task occurrence with the new fingerprint. Task rules snapshot the selection and policy; group edits do not mutate existing task rules. Task UI can also combine saved groups and specify website domains.

Native domain rules require only Screen Time authorization, not NextDNS setup. Up to 50 normalized domains per list; URLs/paths are rejected. Block-all applies to app categories and does not promise to disable essential system services. Screen Time permission and initial app selection still require user interaction. New agent commands require the device to receive them while Planner is foregrounded; previously downloaded task monitors expire independently. Account changes stop global/task sessions and clear the current selection/policy while preserving separately keyed saved groups. Read-back reports configured OS state, not proof that a particular app/site was actually denied. NextDNS remains an optional cloud alternative on the web.

Simulator verification: native group persistence/account isolation, unknown-group rejection, domain normalization/limit, agent configuration, all-app shield, domain filter, stop cleanup, stale/replayed commands, and task-rule save/remove passed on iOS 26.5. Actual real-device enforcement is not claimed by these configuration checks.

Screen Time onboarding now uses one Planner button, “Set up Screen Time,” which presents a full-height native guided sheet: authorization → named app groups → optional location → summary. The previous embedded native rectangle and Cloud/Apple mode tabs were removed; that nested host could receive zero-height layout and appear blank. Closing the sheet returns to Planner. App picking still uses Apple's native picker, inside the setup flow. The native modal also supports agent-requested picking; frontend teardown dismisses it on navigation/logout. iOS 26.5 UI automation verified opening, group name presets, actual picker presentation/dismissal, location-step navigation, Back and Close.

Finishing setup now stores an account-specific completion marker and notifies Planner to refresh a safe native setup summary. Saved group names and optional location appear on the Screen Time page with Edit setup, including after reopening. Existing saved groups/locations also show as configured. Native UI automation verifies Finish → summary → Edit; the browser fixture verifies completion refresh and reload persistence.

Current-location selection retries temporary Core Location `locationUnknown` errors with a bounded timeout; missing simulated GPS produces an actionable simulator/address-search message rather than incorrectly asserting permission was denied. Starting address search clears stale lookup failures and cancels its pending lookup. A simulated NYU-area GPS fix was supplied for local QA, and the actual Core Location callback returned found/valid without saving a test place. No physical location or phone configuration was inferred or changed.
